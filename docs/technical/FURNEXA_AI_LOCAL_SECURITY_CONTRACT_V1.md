# Furnexa AI Local Security Contract V1

**Status:** Proposed security contract. It changes no application code or database.

## 1. Verified Existing Security

- Authentication is session-based in `SecurityLocalDataSource`.
- User, role, and permission records are checked for active state.
- System roles receive permission and scope bypasses.
- Warehouse scopes are exact `ScopeType.warehouse` grants.
- Prompt 23 scopes Sales deliveries and Sales/Return child reads in SQL for non-admin users.
- Prompt 23 also provides empty-scope fail closed behavior for delivery and return reads.
- `audit_logs` supports audit entries and immutability constraints against update/delete.
- The existing local database may be resolved through an environment variable or the stable Windows LocalAppData path.

## 2. Threat Boundary

The Python process is local but must be treated as an untrusted component. A malicious local process or script must not be able to:

- Read SQLite through a direct database client.
- Create or alter Furnexa business records.
- Call Furnexa mutation APIs.
- Read arbitrary local files by path supplied in an API request.
- Receive raw customer or employee data from the AI payload.
- Reuse a previous run's authentication token.
- Bypass Flutter authorization by calling loopback directly.

The loopback API is an implementation detail and must not become a second business API with mutation methods.

## 3. Localhost Binding

- Bind only to `127.0.0.1` or equivalent IPv4 loopback.
- Do not bind to `0.0.0.0`, LAN addresses, or all network interfaces.
- Prefer an ephemeral loopback port.
- Verify the process is the one started by the current Flutter application before serving requests.
- Do not expose a public URL or external route.

## 4. Process Authentication

Use a per-process random secret generated by Flutter:

- Minimum length and cryptographic randomness suitable for a local bearer token.
- Supply through the process environment or stdin handshake; do not place in request URLs or logs.
- Require the token on every analysis request and health/administrative endpoint.
- Rotate or discard it on restart.
- Reject missing, malformed, replayed, or mismatched tokens.

System process isolation and Windows ACL constraints may add protection but do not replace the per-process token and loopback binding.

## 5. Payload Validation

Every request must validate:

- Exact allow-listed request type.
- Contract version.
- Mapping version.
- Date range and date format.
- Maximum row count.
- Maximum request byte size.
- Maximum identity count and horizon length.
- Finite, nonnegative observed quantities.
- Allowed state values only.
- Unique identity/date combinations.
- Duplicate and unknown-field rejection.
- No database path, SQL, file path, executable command, or business mutation field.
- No null where a required field is nonnull.

The following limits require product/security approval:

- Maximum payload bytes.
- Maximum number of series.
- Maximum history range.
- Maximum forecast horizon.
- Maximum concurrent requests.
- Maximum execution duration.

## 6. Python Execution Contract

The local Python process:

- Receives JSON or a fixed IPC request.
- Has no SQLite package or database path argument.
- Cannot receive an arbitrary module or Python expression to execute.
- Runs only a fixed entrypoint and allow-listed analysis objective.
- Runs in the project's existing `.venv` interpreter.
- Must not recreate or replace the virtual environment.
- Must not use external network libraries or network calls.
- Must not persist business-row payloads beyond the configured memory/session lifetime.

## 7. Timeouts and Error Handling

- Flutter sets an overall process timeout.
- Flutter sets separate startup, inference, and shutdown bounds.
- Timeout cancels the request or terminates the process according to the approved policy.
- Flutter never retries mutation operations automatically.
- Python returns structured errors: invalid payload, unsupported contract, insufficient history, process timeout, or internal analysis failure.
- Flutter presents a neutral user-readable error and logs only the sanitized reason.
- Partial or malformed AI results are not displayed as accepted facts.

## 8. Process Lifecycle

- Start Python only when an authorized analysis is requested.
- Prefer one process per application session or one process per approved run.
- Health checks remain localhost-only and token-protected.
- Stop the process on Flutter shutdown or explicit analysis-session end.
- Terminate gracefully, then force-stop only if the approved grace period expires.
- Prevent duplicate processes or require a fixed process lock.
- Never start Python as an elevated or administrator process.

## 9. Permission Policy

### No unnecessary new permission

At design level, `AI_DATA_EXPORT` is **not proposed as a required permission** for the local analysis flow if Flutter's existing authenticated `SALES_VIEW`, `RETURNS_VIEW`, and `QUALITY_VIEW` permissions already define read access and no raw export leaves the local process.

Recommended minimum permission requirement:

- Require `SALES_VIEW` for delivery-demand analysis.
- Require `RETURNS_VIEW` and `QUALITY_VIEW` for verified accepted-return adjustment.
- Require no `SYSTEM_ADMIN` privilege.
- Do not reuse `SYSTEM_ADMIN` for ordinary AI access.
- Do not reuse the existing global Import/Export module.

A dedicated `AI_ANALYZE` permission becomes necessary only if product policy requires AI use to be distinct from ordinary read access. `AI_DATA_EXPORT` is unnecessary if no export artifact is created and no external service receives data.

### Decisions requiring approval

- Whether all authorized Sales readers may run analysis or only a higher-privilege AI role.
- Whether accepted returns require a second approval beyond existing read permissions.
- Whether a persisted AI result or temporary in-memory result requires additional permission.
- Whether audit visibility remains under `AUDIT_VIEW`.

## 10. Audit

Log through `audit_logs`:

- `AI_ANALYSIS_REQUESTED`
- `AI_ANALYSIS_STARTED`
- `AI_ANALYSIS_COMPLETED`
- `AI_ANALYSIS_DENIED`
- `AI_ANALYSIS_FAILED`
- `AI_PROCESS_TIMEOUT`

Each entry should include:

- Sanitized user ID/username snapshot.
- Active role identifier snapshot.
- Contract and mapping versions.
- Purpose and date range.
- Warehouse scope summary.
- Input and result row counts.
- Exclusion reasons as aggregate counts.
- Opaque process/request/result IDs.
- No raw payload or database path.

Audit insertion must be synchronous enough to preserve denied and failed attempts. Audit failure policy requires product approval.

## 11. Data Retention and Cleanup

- Analysis payload memory is release after request completion.
- No row-level payload is persisted unless an approved output contract requires it.
- Temporary payload/result files are avoided.
- If used, temporary files are deleted on success, failure, timeout, and process shutdown.
- Any persisted recommendations retain only approved result fields and fixed retention period.
- Raw source identifiers and relink mappings are not returned to Python.
- Existing historical AI artifacts and benchmark files are preserved and excluded from runtime cleanup.

## 12. No Business Mutation

Python result data must be advisory, descriptive, and non-executable:

- No purchase order suggestion IDs or command objects.
- No direct production operation payload.
- No accounting journal payload.
- No inventory adjustment command.
- No automatic application to SQLite.

Any future operation requires Flutter to call the existing business repository, recheck authorization, and obtain explicit user approval.
